# 07 — DATABASE DESIGN

## 1. Purpose

This document defines the database design for the ResQGrid — Real-Time Emergency Response & Resource Dispatch Engine.

The database is responsible for persistently storing emergency incidents, locations, emergency resources, response teams, capabilities, dispatches, operational states, and historical response information.

The database design must support:

- Incident management
- Emergency resource management
- Response team management
- Resource and team capability management
- Dispatch management
- Resource assignment integrity
- Current operational state tracking
- Historical dispatch tracking
- Multi-criteria dispatch selection
- Concurrent dispatch requests
- JDBC-based database access
- JPA/Hibernate-based persistence
- Transactional consistency
- Reporting and analytical queries
- Future REST and web application integration

The database must use PostgreSQL and SQL as the persistent storage mechanism.

No NoSQL database is part of the initial ResQGrid architecture.

---

## 2. Database Technology

The initial database technology is:

- Database: PostgreSQL
- Database access language: SQL
- JDBC driver: PostgreSQL JDBC Driver
- Direct database access: JDBC
- ORM persistence: JPA/Hibernate
- Application language: Java 21
- Build system: Maven

The database must remain relational throughout the initial project.

The project will intentionally use both JDBC and JPA/Hibernate during development so that database access can be learned and compared at both levels.

The database design must therefore support both:

- Explicit SQL operations through JDBC
- Entity persistence and relationships through JPA/Hibernate

3. `resources`

## 4. Location Table

The `locations` table stores geographic coordinates associated with incidents and emergency resources.

### Table

`locations`

### Columns

#### `id`

- Type: `BIGINT`
- Primary key
- Generated by PostgreSQL identity generation
- Not nullable

#### `latitude`

- Type: `DOUBLE PRECISION`
- Not nullable
- Valid range: `-90` to `90`

#### `longitude`

- Type: `DOUBLE PRECISION`
- Not nullable
- Valid range: `-180` to `180`

### Constraints

Latitude must always be within the valid geographic latitude range.

Longitude must always be within the valid geographic longitude range.

The database should enforce these coordinate boundaries using database constraints.

### Geographic Technology

PostGIS is not part of the initial implementation.

The initial system stores latitude and longitude as numeric values and allows application-level distance calculation.

A specialized PostgreSQL geospatial extension may only be introduced later if the project documentation is updated to require it.

## 5. Incident Table

The `incidents` table stores emergency incidents reported to the ResQGrid system.

### Table

`incidents`

### Columns

#### `id`

- Type: `BIGINT`
- Primary key
- Generated by PostgreSQL identity generation
- Not nullable

#### `description`

- Type: `TEXT`
- Not nullable
- Stores the description of the emergency incident

#### `severity`

- Type: `VARCHAR(20)`
- Not nullable
- Stores the incident severity

Initial valid values:

- `CRITICAL`
- `HIGH`
- `MEDIUM`
- `LOW`

#### `status`

- Type: `VARCHAR(40)`
- Not nullable
- Stores the current incident lifecycle state

Initial valid values:

- `REPORTED`
- `ASSESSED`
- `REQUIREMENTS_DETERMINED`
- `RESPONSE_IN_PROGRESS`
- `RESOLVED`

#### `location_id`

- Type: `BIGINT`
- Foreign key referencing `locations.id`
- Not nullable

#### `created_at`

- Type: `TIMESTAMP`
- Not nullable
- Stores the time at which the incident was created

### Relationships

Each incident has exactly one associated location.

One location may be associated with multiple incidents.

An incident may later have one or more dispatch records associated with it.

## 8. Capability Table

The `capabilities` table stores controlled capability values used for resource and response-team eligibility.

### Table

`capabilities`

### Columns

#### `id`

- Type: `BIGINT`
- Primary key
- Generated by PostgreSQL identity generation
- Not nullable

#### `name`

- Type: `VARCHAR(50)`
- Not nullable
- Unique

### Initial Capability Values

The initial capability catalogue contains:

- `MEDICAL_RESPONSE`
- `FIRE_RESPONSE`
- `RESCUE_OPERATION`

### Capability Meanings

#### `MEDICAL_RESPONSE`

Represents the ability to perform medical emergency response operations.

#### `FIRE_RESPONSE`

Represents the ability to perform fire-related emergency response operations.

#### `RESCUE_OPERATION`

Represents the ability to perform rescue operations.

### Capability Rules

A resource or response team may possess zero or more capabilities.

If an incident requires a mandatory capability, the resource or team must possess that capability before becoming eligible.

Capability matching occurs during filtering before ranking.

Future capability values require a documentation update before implementation.

## 12. Dispatch Status

Dispatch status represents the lifecycle of a dispatch record.

The initial valid dispatch states are:

- `CREATED`
- `IN_PROGRESS`
- `COMPLETED`

### CREATED

The dispatch record has been created but response activity has not yet started.

### IN_PROGRESS

The resource and any associated response team are actively responding to the incident.

### COMPLETED

The dispatch has finished and becomes historical information.

### Active Dispatches

For operational assignment purposes:

- `CREATED` is considered active.
- `IN_PROGRESS` is considered active.
- `COMPLETED` is considered historical.

Active dispatches must be considered when determining whether a resource or response team is already committed.

## 15. Relationships and Cardinality

The database relationships are defined as follows.

### Location and Incident

One location may have many incidents.

Each incident has one location.

Relationship:

`Location 1 -> N Incident`

### Location and Resource

One location may have many resources.

Each resource has one location.

Relationship:

`Location 1 -> N Resource`

### Resource and Capability

One resource may have many capabilities.

One capability may belong to many resources.

Relationship:

`Resource N <-> N Capability`

Implemented using:

`resource_capabilities`

### Response Team and Capability

One response team may have many capabilities.

One capability may belong to many response teams.

Relationship:

`ResponseTeam N <-> N Capability`

Implemented using:

`team_capabilities`

### Incident and Dispatch

One incident may have multiple dispatches.

Each dispatch belongs to one incident.

Relationship:

`Incident 1 -> N Dispatch`

### Resource and Dispatch

One resource may have multiple dispatch records over time.

Each dispatch references one resource.

Relationship:

`Resource 1 -> N Dispatch`

### Response Team and Dispatch

One response team may participate in multiple dispatches.

Each dispatch may reference zero or one response team.

Relationship:

`ResponseTeam 1 -> N Dispatch`

with the response team side being optional for a dispatch.

## 17. Database Constraints

The database must enforce structural integrity wherever the rule can be safely represented at the database level.

### Primary Key Constraints

Every entity table must have a primary key.

Junction tables must use composite primary keys.

### Foreign Key Constraints

All documented relationships must be represented using foreign keys.

### Capability Uniqueness

`capabilities.name` must be unique.

### Coordinate Constraints

Latitude must satisfy:

`-90 <= latitude <= 90`

Longitude must satisfy:

`-180 <= longitude <= 180`

### Controlled Values

Controlled values must only contain supported domain values.

These values correspond to the Java enums defined in the domain model.

### Relationship Integrity

A resource capability relationship must reference an existing resource and an existing capability.

A team capability relationship must reference an existing response team and an existing capability.

A dispatch must reference an existing incident and an existing resource.

An optional response team reference must reference an existing response team when present.

## 19. Resource Assignment Integrity

Resource assignment is a core integrity requirement of ResQGrid.

The database must support the rule that one emergency resource must not be assigned to conflicting active dispatches.

A resource may have multiple historical dispatch records.

Historical dispatches do not make the resource permanently unavailable.

Only active operational assignments affect current availability.

### Active Dispatch States

The following dispatch states are considered active:

- `CREATED`
- `IN_PROGRESS`

The following state is historical:

- `COMPLETED`

### Assignment Rule

A resource marked as available may be selected only after eligibility verification.

Before final assignment, the system must verify that the resource is still eligible.

The final assignment must be performed atomically.

The database must remain consistent if two incidents attempt to assign the same resource concurrently.

The detailed concurrency mechanism is defined in:

`09-CONCURRENCY-DESIGN.md`

The exact locking or transaction strategy is not defined by this document alone.

## 20. History

The database must preserve historical operational information.

Dispatch records serve as the primary historical record of resource assignment.

A completed dispatch must remain stored rather than being deleted merely because the operation has finished.

Historical dispatch information supports:

- Response history
- Resource utilization
- Incident response analysis
- Team participation history
- Reporting
- Operational analytics
- Future performance evaluation

The initial design does not require a separate audit-history table.

Additional audit infrastructure may be introduced later only if the project documentation is updated.

---

## 21. Current State vs Historical State

ResQGrid must distinguish between current operational state and historical information.

### Current State

Current state is represented by the current values stored on domain entities.

Examples:

- Current resource status
- Current response team status
- Current incident status
- Current resource location
- Current team capabilities
- Current resource capabilities

### Historical State

Historical operational activity is represented primarily by dispatch records.

A completed dispatch remains stored as historical information.

### Current Assignments

Current assignments are determined from dispatch records that are still active.

Active dispatches are:

- `CREATED`
- `IN_PROGRESS`

Completed dispatches are historical and do not represent current assignments.

This allows the system to preserve history without incorrectly treating historical work as an active assignment.

## 22. Indexing

Indexes must be based on actual query and filtering requirements rather than being added randomly.

The initial system is expected to query resources by operational suitability and availability.

Potential initial index targets include:

- Resource status
- Resource type
- Resource location
- Dispatch incident
- Dispatch resource
- Dispatch status
- Response team status
- Capability relationships

The final index definitions must support the actual query patterns implemented by the repository and dispatch engine.

Indexes must not be added solely because a column is a foreign key unless the query workload justifies the index.

Composite indexes may be introduced when actual query patterns require multiple-column filtering.

The indexing strategy must be reviewed as the dispatch engine and reporting queries are implemented.

## 24. Distance Calculation

Distance is an important factor in resource selection.

The initial database design stores:

- Latitude
- Longitude

for locations.

The system does not initially use PostGIS or another specialized geospatial database extension.

Distance may be calculated by application logic using persisted coordinates.

The dispatch engine may use calculated distance as one of its ranking factors.

Distance alone must not determine the final dispatch decision.

The dispatch engine must first perform eligibility filtering and then apply the documented multi-criteria ranking process.

If a specialized geospatial implementation becomes necessary later, the database design must be updated before implementation.

## 25. Transaction Requirements

Database transactions are required for operations that modify multiple related pieces of operational state.

The dispatch assignment process is the primary example.

A successful dispatch assignment may involve:

1. Verifying resource eligibility
2. Creating the dispatch record
3. Updating the resource status
4. Updating the response team state when applicable
5. Updating the incident state when required
6. Committing the complete operation

These changes must be treated as one logical operation.

If a required operation fails, the system must not leave a partially completed assignment.

The transaction must either:

- Complete successfully, or
- Roll back the affected changes

The exact transaction mechanism is defined by the concurrency and persistence implementation.

The detailed concurrency strategy is documented in:

`09-CONCURRENCY-DESIGN.md`

## 26. JDBC Requirements

JDBC is part of the initial learning and implementation strategy.

The project must demonstrate direct relational database access using JDBC.

JDBC implementation must include:

- PostgreSQL JDBC driver
- Connection management
- Prepared statements
- Parameterized SQL
- Result-set processing
- Resource cleanup
- SQLException handling
- Transaction management where required

Prepared statements must be used for dynamic input.

Connection lifecycle management must be explicit and safe.

## 28. ORM Performance Considerations

JPA/Hibernate must be used carefully.

The project must avoid blindly loading large object graphs.

The following performance issues must be explicitly considered:

- N+1 query problems
- Unnecessary eager fetching
- Excessive lazy loading
- Large collection loading
- Unnecessary joins
- Repeated database queries
- Missing indexes
- Inefficient JPQL/HQL
- Unnecessary entity updates

Fetch strategies must be selected according to actual use cases.

Lazy loading is preferred where appropriate, but must be handled correctly to avoid `LazyInitializationException`.

The application must not rely on accidental ORM behavior.

Database queries must be reviewed when performance-sensitive dispatch operations are implemented.

## 29. Security

Database security is required even though the initial system is a learning project.

The application must not expose:

- Database passwords
- Database credentials
- Connection secrets
- Internal SQL details
- Stack traces
- Sensitive infrastructure information

through REST or web responses.

Database credentials must be supplied through environment configuration rather than committed into source control.

The project must not store database passwords directly in Git-tracked source files.

The `.gitignore` configuration must prevent accidental committing of local environment files such as:

`.env`

SQL queries involving user-controlled input must use parameterized statements.

Database users should receive only the permissions required by the application.

## 30. Schema Evolution

- A new table
- A new column
- A changed relationship
- A changed constraint
- A new controlled value
- A new index
- A new persistence requirement

the appropriate documentation must be updated first.

The implementation must then follow the updated documentation.

Database schema changes must not be made randomly during coding.
